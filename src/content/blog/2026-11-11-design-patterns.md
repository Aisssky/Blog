### 类之间的关系

#### 关联关系\(Association\)

- 是类与类之间最常用的一种关系，它是一种结构化关系，用于表示一类对象与另一类对象之间有联系。

![image\.png](/images/uploads/design-patterns/image-16.webp)

#### 聚合关系\(Aggregation\)

- 表示一个**整体与部分的关系**。通常在定义一个整体类后，再去分析这个整体类的组成结构，从而找出一些成员类，该整体类和成员类之间就形成了聚合关系。 

![image\.png](/images/uploads/design-patterns/image-44.webp)

#### 组合关系\(Composition\)

- 也表示类之间整体和部分的关系，但是组合关系中部分和整体具有统一的生存期。一旦整体对象不存在，部分对象也将不存在，部分对象与整体对象之间具有同生共死的关系。

![image\.png](/images/uploads/design-patterns/image-7.webp)

#### 依赖关系\(Dependency\)

- 一种使用关系，特定事物的改变有可能会影响到使用该事物的其他事物，在需要表示一个事物使用另一个事物时使用依赖关系。大多数情况下，依赖关系体现在某个类的方法使用另一个类的对象作为参数。

## 软件设计复杂的根本原因

变化：客户需求/市场环境/开发团队/技术平台的变化

而面向对象设计最大的优势在于抵御变化，设计模式的目标就是复用，分解分而治之，抽象。

## 面向对象设计原则\(八大原则\)

1. 依赖倒置原则 **DIP**

    - 高层模块（稳定）不应该依赖于底层模块（变化），二者都依赖于抽象（稳定）；

    - 抽象（稳定）不应该依赖于实现细节（变化），实现细节应该依赖于抽象（稳定）；

2. 开放封闭原则 **OCP**

    - 对扩展开放，对更改封闭

    - 类模块应该是可扩展的，但是不可修改。

3. 单一职责原则 **SRP**

    - 一个类应该仅有一个引起它变化的原因

    - 变化的方向隐含着类的责任

4. Liskov替换原则 **LSP**

    - 子类必须能够替换它们的基类（IS\-A）

    - 继续表达类型抽象

5. 接口隔离原则 **ISP**

    - 不应该强迫客户程序依赖它们不用的方法

    - 接口应该小而完备

6. 优先使用对象组合，而不是继承

    - 类继承通常为“白箱复用”，对象组合通常为“黑箱复用”

    - 继承在某种程度上破坏了封装性，子类父类耦合度高

    - 而对象组合则只要求被组合的对象具有良好定义的接口，耦合度低

7. 封装变化点

    - 使用封装来创建对象之间的分层界

8. 针对接口编程而不是针对实现编程

    - 不将变量类型声明为某个特定的具体类，而是声明为某个接口

    - 客户程序无需获知对象的具体类型，只需要知道对象所具有的接口

    - 减少系统中各部分的依赖关系，从而实现“高内聚，松耦合”的类型设计方案

    - 接口标准化

## GOF\-23 模式

### 分类

#### 从目的来看

- **创建型**（Creational）模式：将对象的部分创建工作延迟到子类或者其他对象，从而应对需求变化为对象创建时具体类实现引来的冲击。**包含**抽象工厂模式、建造者模式、工厂方法模式、原型模式、单例模式

- **结构型**（Structural）模式：通过类继承或者对象组合获得更灵活的结构，从而应对需求变化为对象的结构带来的冲击。**包含**适配器模式、桥接模式、组合模式、装饰模式、外观模式、享元模式、代理模式

- **行为型**（Behavioral）模式：通过类继承或者对象组合来划分类与对象间的职责，从而应对需求变化为多个交互的对象之间的冲击。**包含**职责链模式、命令模式、解释器模式、迭代器模式、中介者模式、备忘录模式、观察者模式、状态模式、策略模式、模板方法模式、访问者模式

![image\.png](/images/uploads/design-patterns/image-62.webp)

#### 从范围来看

- 类模式处理类与子类的静态关系。包含工厂方法模式、适配器模式（类）、解释器模式、模板方法模式

- 对象模式处理对象间的动态关系。包含抽象工厂模式、建造者模式、原型模式、单例模式、适配器模式（对象）、桥接模式、组合模式、装饰模式、外观模式、享元模式、代理模式、职责链模式、命令模式、迭代器模式、中介者模式、备忘录模式、观察者模式、状态模式、策略模式、访问者模式

#### 重构获得模式

##### 关键技法

- 静态 → 多态

- 早绑定 → 晚绑定

- 继承 → 组合

- 编译时依赖 → 运行时依赖

#### ”组件协作“模式

1. 现代软件专业分工之后的第一个结果是“框架与应用分离”，“组件协作”模式通过晚期绑定，来实现框架与应用之间的松耦合，是二者之间协作时常用的模式。

2. 典型模式

    ##### Template Method模板方法

    ###### 定义

    定义一个操作中的算法的骨架（稳定），而将一些步骤延迟\(变化\)到子类中。Template Method使得子类可以不改变\(复用\)一个算法的结构即可重定义\(override 重写\)某些特定步骤。

    ###### 结构

    - AbstractClass: 抽象类 

    - ConcreteClass:  具体子类 

![image\.png](/images/uploads/design-patterns/image-17.webp)

    ###### 总结

    - Template Method模式是一种非常基础性的设计模式，在面向对象系统中有着大量的应用。它用最简洁的机制（虚函数的多态）为很多应用程序框架提供了灵活的扩展点，是代码复用方面的基本实现结构。

    - 除了可以灵活应对子步骤的变化外，“不要调用我，让我调用你”的反向控制结构是Template Method的典型特征。

    - 在具体实现方面，被Template Method调用的方法，可以有任何实现，也可以没有任何实现（抽象方法、纯虚方法），一般将它们设置为protected方法。

    ###### 例题

    **实例一：银行业务办理流程** 

    在银行办理业务时，一般都包含几个基本步骤，首先需要取号排队，然后办理具体业务，最后需要对银行工作人员进行评分。无论具体业务是取款、存款还是转账，其基本流程都一样。现使用模板方法模式模拟银行业务办理流程。

![image\.png](/images/uploads/design-patterns/image-38.webp)

    **实例二：数据库操作模板 **

    对数据库的操作一般包括连接、打开、使用、关闭等步骤，在数据库操作模板类中我们定义了connDB\(\)、openDB\(\)、useDB\(\)、closeDB\(\)四个方法分别对应这四个步骤。对于不同类型的数据库（如SQL Server和Oracle），其操作步骤都一致，只是连接数据库connDB\(\)方法有所区别，现使用模板方法模式对其进行设计。

    ##### Strategy策略模式

    ###### 定义

    定义一系列算法，把它们一个个封装起来，并且使它们可互相替换（变化）。该模式使得算法可独立于使用它的客户程序\(稳定\)而变化（扩展，子类化）。

    ###### 结构

    - Context: 环境类

    - Strategy: 抽象策略类

    - ConcreteStrategy: 具体策略类

![image\.png](/images/uploads/design-patterns/image-59.webp)

    ###### 总结

    - Strategy及其子类为组件提供了一系列可重用的算法，从而可以使得类型在运行时方便地根据需要在各个算法之间进行切换。

    - Strategy模式提供了用条件判断语句以外的另一种选择，消除条件判断语句，就是在解耦合。含有许多条件判断语句的代码通常都需要Strategy模式。

    - 如果Strategy对象没有实例变量，那么各个上下文可以共享同一个Strategy对象，从而节省对象开销。

    ###### 例题

    **实例一：排序策略**

    ##### Observer / Event观察者模式

###### 定义

定义对象间的一种一对多（变化）的依赖关系，以便当一个对象（Subject）的状态发生改变时，所有依赖于它的对象都得到通知并自动更新。

###### 结构

- Subject: 目标

- ConcreteSubject: 具体目标

- Observer: 观察者

- ConcreteObserver: 具体观察者

![image\.png](/images/uploads/design-patterns/image-67.webp)

###### 总结

- 使用面向对象的抽象，Observer模式使得我们可以独立地改变目标与观察者，从而使二者之间的依赖关系达致松耦合。

- 目标发送通知时，无需指定观察者，通知（可以携带通知信息作为参数）会自动传播。

- 观察者自己决定是否需要订阅通知，目标对象对此一无所知。

- Observer模式是基于事件的UI框架中非常常用的设计模式，也是MVC模式的一个重要组成部分。

MVC重要的组成部分，UI框架中经常用到。观察者模式可以用来实现MVC模式，观察者模式中的观察目标就是MVC模式中的模型\(Model\)，而观察者就是MVC中的视图\(View\)，控制器\(Controller\)充当两者之间的中介者\(Mediator\)。当模型层的数据发生改变时，视图层将自动改变其显示内容。

#### “单一职责”模式

在软件组件的设计中，如果责任划分的不清晰，使用继承得到的结果往往是随着需求的变化，子类急剧膨胀，同时充斥着重复代码，这时候的关键是划清责任。

##### 装饰模式

###### 定义

动态（组合）地给一个对象增加一些额外的职责。就增加功能而言，Decorator模式比生成子类（继承）更为灵活（消除重复代码 \& 减少子类个数）。

###### 结构

![image\.png](/images/uploads/design-patterns/image-12.webp)

###### 总结

- 通过采用组合而非继承的手法，Decorator模式实现了在运行时动态扩展对象功能的能力，而且可以根据需要扩展多个功能。避免了使用继承带来的“灵活性差”和“多子类衍生问题”。

- Decorator类在接口上表现为is\-a Component的继承关系，即Decorator类继承了Component类所具有的接口。但在实现上又表现为has\-a Component的组合关系，即Decorator类又使用了另外一个Component类。

- Decorator模式的目的并非解决“多子类衍生的多继承”问题，Decorator模式应用的要点在于解决“主体类在多个方向上的扩展功能”——是为“装饰”的含义。

##### 桥模式

###### 定义

将抽象部分\(业务功能\)与实现部分\(平台实现\)分离，使它们都可以独立地变化。

###### 结构

![image\.png](/images/uploads/design-patterns/image-3.webp)

###### 总结

- Bridge模式使用“对象间的组合关系”解耦了抽象和实现之间固有的绑定关系，使得抽象和实现可以沿着各自的维度来变化。所谓抽象和实现沿着各自纬度的变化，即“子类化”它们。

- Bridge模式有时候类似于多继承方案，但是多继承方案往往违背单一职责原则（即一个类只有一个变化的原因），复用性比较差。Bridge模式是比多继承方案更好的解决方法。

- Bridge模式的应用一般在“两个非常强的变化维度”，有时一个类也有多于两个的变化维度，这时可以使用Bridge的扩展模式。

#### “对象创建”模式

通过“对象创建”模式绕开new，来避免对象创建（new）过程中所导致的紧耦合（依赖具体类），从而支持对象创建的稳定。它是接口抽象之后的第一步工作。

典型模式

##### 简单工厂 Simple Factory

###### 定义

又称为静态工厂方法\(Static Factory Method\)模式，它属于类创建型模式。

在简单工厂模式中，可以根据参数的不同返回不同类的实例。

简单工厂模式专门定义一个类来负责创建其他类的实例，被创建的实例通常都具有共同的父类。 

###### 结构

简单工厂模式包含如下角色：

- **Factory：工厂角色**

- **Product：抽象产品角色**

- **ConcreteProduc**

![image\.png](/images/uploads/design-patterns/image-70.webp)

###### 总结

- 工厂类含有必要的判断逻辑，可以决定在什么时候创建哪一个产品类的实例，客户端可以免除直接创建产品对象的责任，而仅仅“消费”产品；简单工厂模式通过这种做法实现了对责任的分割，它提供了专门的工厂类用于创建对象。

- 客户端无须知道所创建的具体产品类的类名，只需要知道具体产品类所对应的参数即可，对于一些复杂的类名，通过简单工厂模式可以减少使用者的记忆量。

- 通过引入配置文件，可以在不修改任何客户端代码的情况下更换和增加新的具体产品类，在一定程度上提高了系统的灵活性。

- 由于工厂类集中了所有产品创建逻辑，一旦不能正常工作，整个系统都要受到影响。

- 使用简单工厂模式将会增加系统中类的个数，在一定程序上增加了系统的复杂度和理解难度。

- 系统扩展困难，一旦添加新产品就不得不修改工厂逻辑，在产品类型较多时，有可能造成工厂逻辑过于复杂，不利于系统的扩展和维护。

- 简单工厂模式由于使用了静态工厂方法，造成工厂角色无法形成基于继承的等级结构。

##### Factory Method 工厂方法

###### 定义

定义一个用于创建对象的接口，让子类决定实例化哪一个类。

Factory Method使得一个类的实例化延迟（目的：解耦，手段：虚函数）到子类。

###### 结构

- **Product：抽象产品**

- **ConcreteProduct：具体产品**

- **Factory：抽象工厂**

- **ConcreteFactory：具体工厂**

![image\.png](/images/uploads/design-patterns/image-22.webp)

###### 总结

- Factory Method模式用于隔离类对象的使用者和具体类型之间的耦合关系。面对一个经常变化的具体类型，紧耦合关系\(new\)会导致软件的脆弱。

- Factory Method模式通过面向对象的手法，将所要创建的具体对象工作延迟到子类，从而实现一种扩展（而非更改）的策略，较好地解决了这种紧耦合关系。

- Factory Method模式解决“单个对象”的需求变化。缺点在于要求创建方法/参数相同。

##### Abstract Factory抽象工厂

###### 定义

提供一个接口，让该接口负责创建一系列“相关或者相互依赖的对象”，无需指定它们具体的类。

###### 结构

**抽象工厂模式包含如下角色：**

- **AbstractFactory****：抽象工厂**

- **ConcreteFactory****：具体工厂**

- **AbstractProduct****：抽象产品**

- **Product****：具体产品**

![image\.png](/images/uploads/design-patterns/image-20.webp)

###### 总结

- 如果没有应对“多系列对象构建”的需求变化，则没有必要使用Abstract Factory模式，这时候使用简单的工厂完全可以。

- “系列对象”指的是在某一特定系列下的对象之间有相互依赖、或作用的关系。不同系列的对象之间不能相互依赖。

- Abstract Factory模式主要在于应对“新系列”的需求变动。其缺点在于难以应对“新对象”的需求变动。

##### Proxy代理模式

##### **定义**

为其他对象提供一种代理以控制（隔离，使用接口）对这个对象的访问。

##### **结构**

代理模式包含如下角色：

- Subject: 抽象主题角色

- Proxy: 代理主题角色

- RealSubject: 真实主题角色

![image\.png](/images/uploads/design-patterns/image-26.webp)

###### 远程 \(Remote\) 代理

PPT原文定义：为一个位于**不同的地址空间**的对象提供一个本地的代理对象，这个不同的地址空间可以是在同一台主机中，也可是在另一台主机中，远程代理又叫做大使 \(Ambassador\)。

特点/用途：隐藏网络细节，让客户端感觉在调用本地对象。

###### 虚拟 \(Virtual\) 代理

如果需要创建一个资源消耗较大的对象，先创建一个消耗相对较小的对象来表示，真实对象只在需要时才会被真正创建。

特点/用途：**延迟加载（Lazy Loading），优化性能**，节省内存。“图片代理”。客户端先看到一张“小图片”（代理），当真正需要浏览时，才在后台去加载“大图片”（真实主题）。

###### 保护 \(Protect or Access\) 代理

**控制对一个对象的访问**，可以给不同的用户提供不同级别的使用权限。

特点/用途：在访问真实对象前进行权限校验。“论坛权限控制代理”。真实对象 `RealPermission` 只管发帖、看帖，而代理对象 `PermissionProxy` 会先检查 `level`（游客还是注册用户），如果没有权限就直接拦截。这也是去年试卷设计题第5题（文档访问代理）的母本。

###### 缓冲 \(Cache\) 代理

为某一个目标操作的结果提供临时的存储空间，以便多个客户端可以共享这些结果。

特点/用途：提高访问速度，减少重复计算或重复请求。

##### **总结**

- “增加一层间接层”是软件系统中对许多复杂问题的一种常见解决方法。在面向对象系统中，直接使用某些对象会带来很多问题，作为间接层的proxy对象便是解决这一问题的常用手段。

- 具体proxy设计模式的实现方法、实现粒度都相差很大，有些可能对单个对象做细粒度的控制，如copy\-on\-write技术，有些可能对组件模块提供抽象代理层，在架构层次对对象做proxy。

- Proxy并不一定要求保持接口完整的一致性，只要能够实现间接控制，有时候损及一些透明性是可以接受的。

##### Adapter适配器

##### **定义**

将一个类的接口转换成客户希望的另一个接口。Adapter模式使得原本由于接口不兼容而不能一起工作的那些类可以一起工作。

##### **结构**

- **Target：目标抽象类 **

- **Adapter：适配器类 **

- **Adaptee：适配者类 **

- **Client：客户类**

![image\.png](/images/uploads/design-patterns/image-57.webp)

##### **总结**

- 增加了类的透明性和复用性，Adapter模式主要应用于“**希望复用一些现存的类，但是接口又与复用环境要求不一致的情况**”，在遗留代码复用、类库迁移等方面非常有用。

- 将目标类和适配者类解耦，GoF 23 定义了两种Adapter模式的实现结构：对象适配器和类适配器。但类适配器采用“多继承”的实现方式，一般不推荐使用。对象适配器采用“对象组合”的方式，更符合松耦合精神。

- 灵活性和扩展性都非常好，Adapter模式可以实现的非常灵活，不必拘泥于Gof23中定义的两种结构。例如，完全可以将Adapter模式中的“现存对象”作为新的接口方法参数，来达到适配的目的。

- 缺点：对于Java、C\#等不支持多重继承的语言，一次最多只能适配一个适配者类，而且目标抽象类只能为抽象类，不能为具体类，其使用有一定的局限性，不能将一个适配者类和它的子类都适配到目标接口。

##### Mediator中介者

##### **定义**

用一个中介对象来封装（封装变化）一系列的对象交互。中介者使各对象不需要显式的相互引用\(编译时依赖 \-\> 运行时依赖\)，从而使其耦合松散（管理变化），而且可以独立地改变它们之间的交互。

##### **结构**

![image\.png](/images/uploads/design-patterns/image-11.webp)

##### **总结**

- 将多个对象间复杂的关联关系解耦，Mediator模式将多个对象间的控制逻辑进行集中管理，变“多个对象互相关联”为“多个对象和一个中介者关联”，简化了系统的维护，抵御了可能的变化。

- 随着控制逻辑的复杂化，Mediator具体对象的实现可能相当复杂。这时候可以对Mediator对象进行分解处理。

- Façade模式是解耦系统间（单向）的对象关联关系；Mediator模式是解耦系统内各个对象之间（双向）的关联关系。

#### “状态变化”模式

在组件构建过程中，某些对象的状态经常面临变化，如何对这些变化进行有效的管理？同时又维持高层模块的稳定？“状态变化”模式为这一问题提供了一种解决方案。

**典型模式**

##### State状态模式

##### **定义**

允许一个对象在其内部状态改变时改变它的行为。从而使对象看起来似乎修改了其行为。

##### **结构**

- Context: 环境类

- State: 抽象状态类

- ConcreteState: 具体状态类

![image\.png](/images/uploads/design-patterns/image-10.webp)

![image\.png](/images/uploads/design-patterns/image-46.webp)

##### **总结**

- State模式将所有与一个特定状态相关的行为都放入一个State的子类对象中，在对象状态切换时，切换相应的对象；但同时维持State的接口，这样实现了具体操作与状态转换之间的解耦。

- 为不同的状态引入不同的对象使得状态转换变得更加明确，而且可以保证不会出现状态不一致的情况，因为转换是原子性的——即要么彻底转换过来，要么不转换。

- 如果State对象没有实例变量，那么各个上下文可以共享同一个State对象，从而节省对象开销。

##### 例题

**实例一：论坛用户等级 **

在某论坛系统中，用户可以发表留言，发表留言将增加积分；用户也可以回复留言，回复留言也将增加积分；用户还可以下载文件，下载文件将扣除积分。该系统用户分为三个等级，分别是**新手、高手和专家**，这三个等级对应三种不同的状态，这三种状态分别定义如下：

**\(1\) 如果积分小于100分，则为新手状态，**用户可以发表留言、回复留言，但是不能下载文件。如果积分大于等于1000分，则转换为专家状态；如果积分大于等于100分，则转换为高手状态。

**\(2\) 如果积分大于等于100分但小于1000分，则为高手状态**，用户可以发表留言、回复留言，还可以下载文件，而且用户在发表留言时可以获取双倍积分。如果积分小于100分，则转换为新手状态；如果积分大于等于1000分，则转换为专家状态；如果下载文件后积分小于0，则不能下载该文件。

**\(3\) 如果积分大于等于1000分，则为专家状态，**用户可以发表留言、回复留言和下载文件，用户除了在发表留言时可以获取双倍积分外，下载文件只扣除所需积分的一半。如果积分小于100分，则转换为新手状态；如果积分小于1000分，但大于等于100，则转换为高手状态；如果下载文件后积分小于0，则不能下载该文件。

##### Memento备忘录

##### **定义**

在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态。这样以后就可以将该对象恢复到原先保存的状态。

##### **结构**

![image\.png](/images/uploads/design-patterns/image-52.webp)

##### **总结**

- 备忘录（Memento）存储原发器（Originator）对象的内部状态，在需要时恢复原发器状态。

- Memento模式的核心是信息隐藏，即Originator需要向外接隐藏信息，保持其封装性。但同时又需要将状态保持到外界（Memento）。

- 由于现代语言运行时（如C\#、Java等）都具有相当的对象序列化支持，因此往往采用效率较高、又较容易正确实现的序列化方案来实现Memento模式。

#### “数据结构”模式

常常有一些组件在内部具有特定的数据结构，如果让客户程序依赖这些特定的数据结构，将极大地破坏组件的复用。这时候，将这些特定数据结构封装在内部，在外部提供统一的接口，来实现与特定数据结构无关的访问，是一种行之有效的解决方案。

**典型模式**

##### Composite组合模式

##### **定义**

将对象**组合成树形结构**以表示“部分\-整体”的层次结构。Composite使得用户对单个对象和组合对象的使用具有一致性（稳定）。

##### **结构**

组合模式包含如下角色：

- **Component: 抽象构件**

- **Leaf: 叶子构件**

- **Composite: 容器构件**

- **Client: 客户类**

- 容器对象与抽象构件类之间还建立一个聚合关联关系，在容器对象中既可以包含叶子，也可以包含容器，以此实现递归组合，形成一个树形结构。

![image\.png](/images/uploads/design-patterns/image-18.webp)

##### **总结**

- Composite模式采用树形结构来实现普遍存在的对象容器，从而将“一对多”的关系转化为“一对一”的关系，使得客户代码可以一致地（复用）处理对象和对象容器，无需关心处理的是单个的对象，还是组合的对象容器。

- 将“客户代码与复杂的对象容器结构”解耦是Composite的核心思想，解耦之后，客户代码将与纯粹的抽象接口——而非对象容器的内部实现结构——发生依赖，从而更能“应对变化”。

- Composite模式在具体实现中，可以让父对象中的子对象反向追溯；如果父对象有频繁的遍历需求，可使用缓存技巧来改善效率。

- 使设计变得更加抽象，对象的业务规则如果很复杂，则实现组合模式具有很大挑战性，而且不是所有的方法都与叶子对象子类都有关联。增加新构件时可能会产生一些问题，很难对容器中的构件类型进行限制。

##### Iterator迭代器

##### **定义**

提供一种方法顺序访问一个聚合对象中的各个元素，而又不暴露（稳定）该对象的内部表示。

##### **结构**

![image\.png](/images/uploads/design-patterns/image-19.webp)

##### **总结**

- 迭代抽象：访问一个聚合对象的内容而无需暴露它的内部表示。

- 迭代多态：为遍历不同的集合结构提供一个统一的接口，从而支持同样的算法在不同的集合结构上进行操作。

- 迭代器的健壮性考虑：遍历的同时更改迭代器所在的集合结构，会导致问题。

##### Chain of Resposibility职责链

##### **定义**

使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递请求，直到有一个对象处理它为止。

##### **结构**

- Handler: 抽象处理者

- ConcreteHandler: 具体处理者

- Client: 客户类

![image\.png](/images/uploads/design-patterns/image-15.webp)

##### **总结**

- Chain of Responsibility 模式的应用场合在于“一个请求可能有多个接受者，但是最后真正的接受者只有一个”，这时候请求发送者与接受者的耦合有可能出现“变化脆弱”的症状，职责链的目的就是将二者解耦，从而更好地应对变化。

- 应用了Chain of Responsibility 模式后，对象的职责分派将更具灵活性。我们可以在运行时动态添加/修改请求的处理职责。

- 如果请求传递到职责链的末尾仍得不到处理，应该有一个合理的缺省机制。这也是每一个接受对象的责任，而不是发出请求的对象的责任。

#### "行为变化"模式

在组件的构建过程中，组件行为的变化经常导致组件本身剧烈的变化。“行为变化”模式将组件的行为和组件本身进行解耦，从而支持组件行为的变化，实现两者之间的松耦合。

**典型模式**

##### Visitor访问器

##### **定义**

表示一个作用于某对象结构中的各元素的操作。使得可以在不改变（稳定）各元素的类的前提下定义（扩展）作用于这些元素的新操作（变化）。

##### **结构**

![image\.png](/images/uploads/design-patterns/image-69.webp)

##### **总结**

- Visitor模式通过所谓双重分发（double dispatch）来实现在不改变（不添加新的操作\-编译时）Element类层次结构的前提下，在运行时透明地为类层次结构上的各个类动态添加新的操作（支持变化）。

- 所谓双重分发即Visitor模式中间包括了两个多态分发（注意其中的多态机制）：第一个为accept方法的多态辨析；第二个为visitElementX方法的多态辨析。

- Visitor模式的最大缺点在于扩展类层次结构（增添新的Element子类），会导致Visitor类的改变。因此Visitor模式适用于“Element类层次结构稳定，而其中的操作却经常面临频繁改动”。

##### Command命令模式

##### **定义**

将一个请求\(行为\)封装为一个对象，从而使你可用不同的请求对客户进行参数化；对请求排队或记录请求日志，以及支持可撤销的操作。

##### **结构**

Command（抽象命令类）

ConcreteCommand（具体命令类）

Invoker（调用者）

Receiver（接收者）

![image\.png](/images/uploads/design-patterns/image-35.webp)

##### **总结**

- Command模式的根本目的在于将“行为请求者”与“行为实现者”解耦，在面向对象语言中，常见的实现手段是“将行为抽象为对象”。

- 实现Command接口的具体命令对象ConcreteCommand有时候根据需要可能会保存一些额外的状态信息。通过使用Composite模式，可以将多个“命令”封装为一个“复合命令”MacroCommand。

- Command模式与C\+\+中的函数对象有些类似。但两者定义行为接口的规范有所区别：Command以面向对象中的“接口\-实现”来定义行为接口规范，更严格，但有性能损失；C\+\+函数对象以函数签名来定义行为接口规范，更灵活，性能更高。

## 软件体系结构

### 一、软件体系结构概述

#### 体系结构分层

软件体系结构包含：

- 数据访问层

- 业务逻辑层

- 展现层

- 门户层：内部门户、外部门户

- 应用层：采购管理、库存管理、供应商管理、合同管理

- 支撑层：流程引擎、4A 和权限管理

- 应用层、平台层、资源层

#### 软件体系结构的动机

软件体系结构的动机包括：

- 功能模块规模大

- 需求复杂、变化频繁

- 形成大规模复杂软件系统

核心结论：

> 总体的系统结构设计比计算算法和数据结构的选择更为重要。
> 
> 

#### 软件体系结构并非凭空出现

软件体系结构是为解决软件发展中的痛点而生：

1. **软件危机**

20 世纪 60—80 年代，软件规模扩大后出现的系统性困境。

2. **构件与重用**

可独立复用、具有明确功能边界的软件单元。

3. **体系结构兴起**

为统筹构件协作而生，解决宏观协作问题。

规模扩大的必然产物：

> 当系统规模超过 10 万行代码后，仅靠模块化编程无法解决模块间如何协作、系统如何扩展等宏观问题。
> 
> 

借鉴建筑工程方法学：

> 软件体系结构借鉴了建筑工程的框架结构思想，遵循“先整体设计，后细节实现”的原则。
> 
> 

#### 软件危机

软件危机是 20 世纪 60 年代至 80 年代，软件规模扩大后出现的系统性困境，也是体系结构发展的直接动因。

|表现|说明|案例|
|---|---|---|
|进度与计划脱节|项目实际进度严重偏离原定计划，导致交付延期|IBM OS/360|
|成本与预算超支|项目实际成本远超初期预算，资源浪费严重|F\-16 战斗机软件|
|质量与需求不符|软件功能无法满足用户需求，系统稳定性差|早期银行 ATM 系统：未考虑并发访问的架构设计，高峰期频繁崩溃，用户取款数据丢失，本质是忽略了系统可靠性的宏观规划|

核心结论：

> 软件危机的根源并非代码写得不好，而是缺乏对软件整体结构的设计。当系统规模超过 10 万行代码后，仅靠模块化编程无法解决模块间如何协作、系统如何扩展等宏观问题。
> 
> 

#### 构件与软件重用

构件是软件体系结构的基本积木，而重用是构件化思想的核心目标，二者共同推动体系结构向高效化发展。

##### 构件的定义

可独立复用、具有明确功能边界的软件单元，如 Java 中的 Jar 包、Python 中的 Wheel 包、前端的 Vue 组件。

特点：

- 黑箱特性：使用者无需关心内部实现，仅需调用接口。

- 标准化：接口格式统一，可在不同系统中复用。

示例代码：

```Java
// 示例：使用 Apache Commons 组件
import org.apache.commons.lang3.StringUtils;

public class ReuseExample {
    public boolean isValidString(String input) {
        return StringUtils.isNotBlank(input);
    }
}
```

##### 构件重用的层次

- 代码级重用：函数、类库的重用

- 组件级重用：DLL、JAR 包等的重用

- 框架级重用：Spring、React 等框架的重用

- 架构级重用：设计模式、体系结构风格的重用

##### 软件重用的价值

解决“重复造轮子”的问题，以 Spring 框架为例：

- **效率提升**：Spring 的 `@Service`、`@Repository` 等注解构件，可直接复用“业务逻辑封装”“数据库访问”功能，开发者无需从零编写 JDBC 连接代码。

- **质量保障**：复用经过大量验证的构件，如 Apache Commons 工具包的字符串处理构件，可降低代码 bug 率。这些构件已在数百万系统中测试，稳定性远高于自定义代码。

- **维护便捷**：当复用的构件需升级，如修复安全漏洞，仅需替换构件版本，无需修改调用代码。比如将 Spring Boot 从 2\.0 升级到 3\.0，只需修改 Maven 依赖版本号。

#### 构件与模块的区别

很多初学者会混淆“构件”与“模块”。二者核心区别在于：

- 模块是“系统内部的功能划分”，如一个订单模块，不可独立脱离系统复用。

- 构件是“跨系统的可复用单元”，如一个通用的订单支付构件，可在电商、外卖等不同系统中使用。

|类别|典型例子|
|---|---|
|模块|一个 MVC 框架中的 Model 层、View 层、Controller 层；一个 Java 项目中的 `order-service` 包；一个前端项目中的“用户管理”模块|
|构件|一个可复用的日志库，如 Log4j；一个第三方支付 SDK，如支付宝 SDK；一个独立的微服务，如“库存管理服务”；一个 UI 组件库，如 Ant Design 的 Button 组件|

#### 软件体系结构的兴起与发展

|发展阶段|时间范围|核心特征|典型案例|
|---|---|---|---|
|结构化阶段|1970s—1980s|以“过程”为核心，构件按“功能流程”组织，如输入→处理→输出|早期工资管理系统，按“录入员工信息→计算工资→生成报表”流程组织构件|
|面向对象阶段|1990s—2000s|以“对象”为核心，构件按“数据 \+ 行为”封装，但缺乏宏观协作规则|Java Swing 桌面应用，虽有“窗口对象”“按钮对象”，但未定义对象间的全局交互逻辑|
|体系结构阶段|2000s 至今|以“整体结构”为核心，明确构件、连接子、约束，形成可复用的设计模式|微服务体系结构，明确“服务构件”“API 网关连接子”“服务注册与发现约束”|

软件体系结构发展历史中的开发模式与时代特征：

- 高级语言 → 面向过程开发 → 面向对象开发 → 面向服务开发 → 云与移动服务开发 → 智能化软件开发

- 系统构成演进：

    - 算法 \+ 数据结构

    - 子程序 \+ 子程序

    - 对象 \+ 对象

    - 构件 \+ 连接

    - 服务 \+ 服务总线

- 时代特征：

    - 工程化

    - 工业化

    - 协作化

- 开发组织范围：

    - 个人

    - 小组

    - 企业

    - 众包

#### 什么是软件体系结构

软件工程领域权威学者 Shaw 和 Garlan 给出定义：

> 软件体系结构是系统的一个或多个结构，包括构件、构件间的连接子，以及构件和连接子的约束。
> 
> 

结构示意：

- 软件体系结构

    - 构件

        - 处理构件

        - 数据构件

    - 连接件

        - 调用返回

        - 消息传递

        - 数据流

    - 约束

        - 拓扑约束

        - 行为约束

#### 软件体系结构关注的核心维度

*软件体系结构不关注“代码如何写”，如循环、判*断的实现，而关注“系统如何设计”的宏观问题，核心包括 3 个维度：

1. **结构设计**

构件如何划分，如电商系统拆分为“用户、商品、订单、支付”4 大构件；连接子如何选择，如 API 或消息队列。

2. **质量属性**

如何通过结构设计满足“高可用”“高并发”需求，如为支付服务设计“集群部署”构件，应对高峰期流量。

3. **演化能力**

如何设计结构，让系统能“低成本升级”，如新增“优惠券服务”时，无需修改原有订单、支付服务。

#### 当前软件体系结构的研究方向

当前软件体系结构的研究紧密结合云计算、大数据等技术趋势，核心方向包括：

- **微服务体系结构**：将系统拆分为“独立部署的小服务”，如电商的每个服务单独部署，解决传统单体系统“升级难、扩展难”问题，代表技术有 Spring Cloud、Dubbo。

- **云原生体系结构**：针对云计算环境设计，强调“容器化”，如 Docker；“动态扩缩容”，如 Kubernetes，让构件能在云环境中高效运行。

- **领域驱动设计（DDD）与体系结构结合**：以“业务领域”为核心划分构件，如金融系统按“账户、交易、风控”领域划分服务，让结构与业务逻辑更贴合，减少后期修改成本。

## 二、软件体系结构建模与风格

### 1\. “4\+1”建模思想

“4\+1”模型由 Rational 公司提出，通过“4 个核心视图 \+ 1 个场景视图”，从不同维度描述体系结构，覆盖开发、测试、运维全流程需求。

本质逻辑：

> 场景视图是“需求入口”，4 个核心视图是“需求落地”——先通过场景明确“用户要做什么”，再通过 4 个视图明确“系统要怎么设计”。
> 
> 

“4\+1”视图包括：

- 场景视图（“4\+1”的“1”）

- 逻辑视图

- 开发视图

- 进程视图

- 物理视图

不同视图面向不同人员：

- 最终用户：功能需求

- 编程人员：软件管理

- 系统集成人员：性能、可扩充性、吞吐量等

- 系统工程人员：系统拓扑、安装、通信等

### 2\. 场景视图（Scenarios View）

- 描述系统在不同情景下的使用场景。

- 关注系统的用例、用户交互和系统行为。

- 包括用户界面、用例场景、用户需求等。

- 用于表示系统的功能需求、用户交互和系统行为

### 3\. 逻辑视图（Logical View）

- 描述系统的功能、组件和它们之间的关系。

- 主要关注系统的静态结构，包括类、接口、包、模块等。

- 用于表示系统的组织结构、模块划分和关系。

图示元素包括：

- 构件：类、类服务、参数化类、类层次

- 连接件：关联、包含/聚集、使用、继承、实例

### 4\. 进程视图（Process View）

- 描述系统的并发性和分布性。

- 关注系统在运行时的行为，包括系统的运行时进程、线程、节点、通信方式等。

- 用于表示系统的并发性、分布性、通信和同步方式。

图示元素包括：

- 构件：进程、简化进程、循环进程

- 连接件：未指定、消息、远程过程调用、双向消息、事件广播

### 5\. 物理视图（Physical View）

- 描述系统的部署和配置。

- 关注系统在物理计算资源上的部署，包括硬件、网络、服务器、存储等。

- 用于表示系统的部署拓扑、配置和资源分配。

### 6\. 开发视图（Development View）

- 描述系统的软件开发过程。

- 关注软件的开发、构建和部署过程，包括开发环境、版本控制、构建工具、编译器等。

- 用于表示系统的开发工程、构建过程和开发环境。

## 三、软件体系结构模型风格

#### 软件体系结构风格定义

- describes a class of architectures

描述一类体系结构

- independent on the problems

独立于实际问题，强调软件系统中通用的组织结构

- found repeatedly in practice

在实践中被多次应用

- a package of design decisions

是若干设计思想的综合

- has known properties that permit reuse

具有已经被熟知的特性，并且可以复用

#### 批处理风格

批处理风格：数据“一次性输入、一次性处理、一次性输出”，适用于“离线数据处理”场景。

特点：

- Processing steps are independent programs

每个处理步骤是一个独立的程序。

- Each step runs to completion before next step starts

每一步必须在前一步结束后才能开始。

- Data transmitted as a whole between steps

数据必须是完整的，以整体的方式传递。

#### 管道—过滤器风格

管道—过滤器风格：

- 数据源（Data source）

- 管道（Pipes）

- 过滤器（Filters）

- 数据终止点（Data sink）

场境

> 数据源源不断地产生，系统需要对这些数据进行若干处理，如分析、计算、转换等。
> 
> 

解决方案：

- 把系统分解为几个序贯的处理步骤，这些步骤之间通过数据流连接，一个步骤的输出是另一个步骤的输入。

- 每个处理步骤由一个过滤器构件（Filter）实现。

- 处理步骤之间的数据传输由管道（Pipe）负责。

- 每个处理步骤（过滤器）都有一组输入和输出，过滤器从管道中读取输入的数据流，经过内部处理，然后产生输出数据流并写入管道中。

### 分层体系结构风格

典型分层结构：3 层架构，软件领域最常用。以 Web 管理系统为例：

|层次|核心功能|典型技术/构件|依赖关系|
|---|---|---|---|
|表现层 Presentation Layer|与用户交互，展示数据、接收请求|前端：HTML/CSS/JS、Vue；后端：JSP、Thymeleaf|依赖业务逻辑层，不直接依赖数据访问层|
|业务逻辑层 Business Logic Layer|处理核心业务规则，协调数据流转|Java：Service 类；Python：Service 函数|依赖数据访问层，为表现层提供服务|
|数据访问层 Data Access Layer|与数据库交互，执行增删改查 CRUD|Java：DAO 类、MyBatis；Python：ORM 框架 SQLAlchemy|不依赖其他层，仅为业务逻辑层提供数据服务|

分层系统的交互遵循“请求—响应”的单向流程。以“用户查询商品信息”为例：

1. 用户在表现层，如 Vue 页面，输入“商品 ID”，点击“查询”按钮，表现层接收请求。

2. 表现层将请求参数，商品 ID，传递给业务逻辑层，如 `GoodsService` 的 `getGoodsById` 方法。

3. 业务逻辑层调用数据访问层，如 `GoodsDAO` 的 `selectById` 方法，请求查询数据库。

4. 数据访问层执行 SQL：`SELECT * FROM goods WHERE id = ?`，从数据库获取商品数据，返回给业务逻辑层。

5. 业务逻辑层对数据进行简单处理，如格式化价格为“¥99\.00”，返回给表现层。

6. 表现层将处理后的数据展示在页面上，如显示商品名称、价格、库存。

### 客户机/服务器（C/S）体系结构

C/S 结构将系统分为“客户机”（Client）和“服务器”（Server）两部分：

- 客户机负责“界面展示与部分逻辑”

- 服务器负责“数据存储与核心逻辑”

按功能划分，C/S 可分为二层结构和三层结构。

#### 二层 C/S 结构

二层 C/S 结构：客户机 \+ 数据库服务器，客户机直接与数据库交互。

案例：早期桌面版 QQ，2000—2010 年。

- 客户机：桌面客户端，安装在用户电脑上，负责界面展示，如聊天窗口、联系人列表，以及本地消息存储。

- 服务器：数据库服务器，存储用户信息、聊天记录。

- 交互流程：用户发送消息 → 客户机将消息发送到服务器 → 服务器存储消息 → 服务器将消息推送给接收方客户机。

- 优点：部署简单，适合小规模用户。

- 缺点：客户端升级麻烦，需用户手动下载安装新版本；安全性差，客户机直接访问数据库，易泄露数据。

#### 三层 C/S 结构

三层 C/S 结构：客户机 \+ 应用服务器 \+ 数据库服务器，应用服务器负责业务逻辑，隔离客户机与数据库。

案例：企业 ERP 系统，如用友 U8。

- 客户机：桌面客户端，安装在员工电脑上，负责界面交互，如录入销售订单。

- 应用服务器：部署在企业内网，负责业务逻辑，如计算订单金额、验证库存。

- 数据库服务器：存储 ERP 系统的所有业务数据，如订单、库存、财务。

- 交互流程：员工录入订单 → 客户机将订单数据发送到应用服务器 → 应用服务器验证库存，调用数据库服务器 → 库存充足则生成订单 → 应用服务器将订单数据存入数据库服务器 → 返回“订单创建成功”给客户机。

### B/S 结构

B/S 结构是 C/S 的“简化版”：

- 客户端为“浏览器”，如 Chrome、Edge，无需安装专用软件。

- 服务器分为“Web 服务器”和“数据库服务器”。

案例：淘宝网页版。

- 客户端：浏览器，用户通过网址 `www.taobao.com` 访问系统，无需安装“淘宝客户端”。

- Web 服务器：部署在阿里云，负责处理请求，如解析用户搜索“手机”的请求，返回页面数据。

- 数据库服务器：存储商品信息、用户订单等数据。

- 交互流程：用户在浏览器搜索“手机”→ 浏览器将请求发送到 Web 服务器 → Web 服务器调用数据库服务器查询“手机类商品”→ 数据库服务器返回商品数据 → Web 服务器生成 HTML 页面 → 浏览器展示页面。

### 混合结构

混合结构结合了 C/S 的“高性能”和 B/S 的“便捷性”，适用于“部分用户需复杂操作、部分用户需简单访问”的场景。

案例：医院管理系统。

- C/S 部分：医生工作站，安装专用客户端。

    - 功能需求：复杂操作，如编辑电子病历、查看医学影像，需高性能、低延迟。

    - 优势：客户端可本地处理大量数据，如医学影像的渲染，操作流畅。

- B/S 部分：患者查询系统，通过浏览器访问。

    - 功能需求：简单操作，如查询挂号记录、查看检查报告，无需安装客户端。

    - 优势：患者在家即可访问，无需到医院或安装软件。

## 四、MVC 体系结构

MVC 的出现，是为解决早期 Web 开发“表现与逻辑混杂”的问题，其演变过程分为 2 个阶段。

### 1\. Model1 模式

时间：1990s—2000s。

结构：JSP \+ JavaBean，表现与逻辑混杂。

- JSP 页面既负责界面展示，HTML，又负责业务逻辑，Java 代码。

- JavaBean 仅负责数据存储。

问题：

以用户登录功能为例，JSP 页面中既有“用户名输入框”的 HTML 代码，又有“判断用户名密码是否正确”的 Java 代码。后期修改登录逻辑时，需在 HTML 中找 Java 代码，维护成本极高。

交互流程：

1. request

2. jsp 取请求参数

3. 调用业务逻辑方法

4. 数据返回后渲染页面

5. response

### 2\. Model2 模式

时间：2000s 至今

结构：MVC，表现与逻辑分离。

- 将 Model1 中的“逻辑部分”拆分到 Controller。

- “数据部分”强化为 Model。

- “界面部分”保留为 View。

- 三者各司其职，解决耦合问题。

优势：

以用户登录功能为例：

- View 负责“登录表单”。

- Controller 负责“接收请求、调用逻辑”。

- Model 负责“用户数据与验证逻辑”。

- 修改登录逻辑时，仅需修改 Controller 和 Model，无需修改 View。

交互流程：

1. 客户端请求

2. Servlet 接收

3. 调用业务逻辑

4. 转发 JSP

5. 响应客户端

### 3\. MVC 体系结构组成

|组成部分|核心职责|案例：用户登录功能|技术实现：Java Spring MVC|
|---|---|---|---|
|Model 模型|1\. 存储数据，实体类；2\. 处理业务逻辑，服务类|1\. `User` 实体类，存储用户名、密码；2\. `UserService` 类，验证用户名密码是否正确|实体类：`public class User { private String username; private String password; }`；服务类：`@Service public class UserService { public boolean checkLogin(String username, String password) { return "admin".equals(username) && "123456".equals(password); } }`|
|View 视图|1\. 展示界面，用户可见；2\. 传递用户输入，表单|1\. 登录页面 `login.jsp`，包含用户名、密码输入框和提交按钮；2\. 首页 `index.jsp`，展示“欢迎您，admin！”|JSP 页面：`login.jsp` 用 `<form>` 标签传递输入，`index.jsp` 用 `${username}` 展示数据|
|Controller 控制器|1\. 接收用户请求；2\. 调用 Model 处理业务；3\. 选择 View 返回|1\. 接收 `/login` 请求，用户点击登录按钮；2\. 调用 `UserService` 的 `checkLogin` 方法；3\. 验证成功→返回 `index.jsp`，失败→返回 `login.jsp`|`@Controller public class UserController { @Autowired private UserService userService; @RequestMapping("/login") public String login(String username, String password, Model model) { if(userService.checkLogin(username,password)) { model.addAttribute("username",username); return "index"; } else { model.addAttribute("error","用户名或密码错误"); return "login"; } } }`|

### 4\. MVC 完整交互流程：以用户登录为例



1. 用户输入用户名密码，点击“登录”按钮，提交 POST 请求到 `/login`。

2. View，`login.jsp`，发送 HTTP POST `/login`，参数如 `username=admin, password=123456`。

3. DispatcherServlet 转发请求给 login 方法，传递请求参数。

4. Controller，`UserController`，调用 `checkLogin(admin, 123456)`。

5. Model，`UserService`，返回 `true`，验证成功。

6. Controller 返回视图名称 `"index"`，模型属性 `username="admin"`。

7. DispatcherServlet 解析视图，调用 `index.jsp`，传递模型数据。

8. 展示 HTML 页面：“欢迎您，admin！”。
