## STL(Standard Template Library)

### 1、标准库以头文件方式呈现

- C++标准库的头文件，不带副档名（.h）

- 新式C头文件不带.h，但加 c 前缀；例如 #include \<cstdio\>

- 旧式C头文件仍然可用，兼容用；例如#include \<stdio.h\>

### 2、新式头文件内的组件封装于namespace "std";

- using namespace std;

把标准命名空间 `std` 里的名字“引入”当前作用域，使可以省略 `std::` 前缀，编译器会把这些名字当作在 `std` 里查找，于是等价于：

- using std::cout;

只是名字查找的便利写法，不会加载任何库，也不会复制代码。它只是省略前缀的语法便利，不是必须的。实际工程中更推荐显式写 `std::`，或者在局部按需 `using std::vector;`，尤其不要在头文件里写 `using namespace std;`。

- 当然，在实际的工程中，业务代码几乎完全不会使用原生STL，比如UE就有自己的组件，例如TArray，FString，TMap等，与GC和反射系统深度集成的这样的一套新东西，我们之后再探讨[UE中对于容器的处理](https://devpress.csdn.net/awstech/6a91f06c3bda720d4b35c87a.html)。

### 复杂度

目前常见的 Big-oh 有下列几种情形：

1. O(1)或O(c)：称为常数时间(constant time)

2. O(n)：称为线性时间(linear time)

3. O(log₂n)：称为次线性时间(sub-linear time)

4. O(n²)：称为平方时间(quadratic time)

5. O(n³)：称为立方时间(cubic time)

6. O(2ⁿ)：称为指数时间(exponential time)

7. O(nlog₂n)：介于线性及二次方成长的中间之行为模式



### C++11 新特性

- 自动类型推断（auto）：引入了auto关键字，可以根据变量初始化表达式的类型自动推断变量的类型，使得代码更具灵活性和可读性。

```C++
// C++98 写法
vector<int>::iterator it = v.begin();
// C++11 写法
auto it = v.begin();

for (auto x : v) { ... }        // 拷贝一份（修改不影响原容器）
for (auto& x : v) { x *= 2; }   // 引用（能改到原元素）
for (const auto& x : v) { ... } // 只读，且不拷贝（遍历大对象首选）
```

- 范围for循环：通过for(element：container)语法，允许直接遍历容器中的每个元素，简化了迭代操作，减少了代码量。

auto类型推导的原理是什么？

auto类型推导的原理：编译器根据初始值来推算变量的类型，要求用auto定义变量时必须有初始值。编译器推断出来的auto类型有时和初始值类型并不完全一样，编译器会适当改变结果类型使其更符合初始化规则。**auto 会剥掉引用和顶层 const，要保留就自己写 auto& / const auto&**。想知道“原样类型”，用 decltype。

###### 底层

###### 核心数据结构

```C++
template<class T, class Alloc = allocator<T>>
class vector {
    T* begin_;      // 指向第一个元素
    T* end_;        // 指向最后一个元素的下一个位置（size 的边界）
    T* cap_end_;    // 指向已分配内存的末尾（capacity 的边界）
};
```

```Plain Text
size()     = end_ - begin_;
capacity() = cap_end_ - begin_;
empty()    = begin_ == end_;
```

> **注意 end() 的位置**：它指向**最后一个元素的下一个位置**，是“哨兵”，不能解引用（*v.end() 是未定义行为）。所以区间永远是**左闭右开** [begin, end)——这也是 STL 所有算法统一约定的区间形式。
> 
> 

- `size` 以内是“已构造对象”；

- `size` 到 `capacity` 之间是“已分配但未构造的原始内存”；

- 分配器负责“分配原始内存”和“构造/析构对象”这两件事的分离。

###### 扩容机制

当 `size() == capacity()` 时，再插入元素就必须扩容。以 `push_back` 为例：

```JavaScript
void push_back(const T& x) {
    if (end_ != cap_end_) {
        // 还有空闲槽位，直接原地构造
        construct(end_, x);
        ++end_;
    } else {
        // 满了，扩容
        reallocate_and_push_back(x);
    }
}
```

1. 申请一块更大的新内存（new_capacity）

2. 把旧元素“移动/拷贝”到新内存

3. 在新内存末尾构造新元素

4. 析构旧内存上的所有元素

5. 释放旧内存

6. 更新 begin_ / end_ / cap_end_

###### 迭代器失效规则

所以迭代器失效的本质就是是否扩容？并不是，更准确地说：

> 扩容是导致“全部迭代器失效”的强原因之一，但迭代器失效的本质不是“是否扩容”，而是“该迭代器所指向的元素地址是否改变 / 元素是否被销毁 / 底层存储结构是否被破坏”。
> 
> 

对 `vector` 来说，因为迭代器本质上就是（包装过的）指针，所以可以理解为：

> 迭代器失效的本质 = 这个迭代器指向的内存位置，在操作之后不再对应原来那个元素，或者不再合法。
> 
> 

扩容只是让“所有元素地址都变了”的一种情况。未扩容的 `insert`、`erase`、`resize` 缩小、`clear` 同样会导致失效。

##### Deque

双端队列是一个具有两端操作的抽象数据类型，可以在队列的头部和尾部进行元素的插入、删除和弹出等操作。通常用deque来表示，具有队列和栈两种数据结构的特点

是分段连续容器，每一段是一个**buffer**,迭代器每走一步都要先判断指定的位置position是否走到了边界，当迭代器走到了边界的时候，不管是头还是尾，要靠指针指回**控制中心**……

###### 底层

[深入解析：浅谈deque的底层机制](https://www.cnblogs.com/ljbguanli/p/19379930) 

```C++
//如果 n 不为 0，传回 n，表示 buffer size 由使用者自定。
//如果 n 为 0，表示 buffer size 使用预设值，那么
//   如果 sz (sizeof(value_type)) 小于 512，传回 512/sz。
//   如果 sz 不小于 512，传回 1。
inline size_t __deque_buf_size(size_t n, size_t sz)
{
    return n != 0 ? n : (sz < 512 ? size_t(512 / sz) : size_t(1));
}
```

**迭代器**

```C++
template <class T, class Ref, class Ptr, size_t BufSiz>
struct __deque_iterator {
    typedef random_access_iterator_tag iterator_category;  //(1)
    typedef T value_type;                                  //(2)
    typedef Ptr pointer;                                   //(3)
    typedef Ref reference;                                 //(4)
    typedef size_t size_type;
    typedef ptrdiff_t difference_type;                     //(5)
    typedef T** map_pointer;
    typedef __deque_iterator self;

    T* cur;                             *// 当前缓冲区中的当前位置*
    T* first;                             *// 当前缓冲区起始*
    T* last;                             *// 当前缓冲区末尾*
    map_pointer node;                  *// 指向中控数组中的某个槽位*
    ...
};
```

**类骨架**

通过 `map` 这个中控台，将不连续的内存（多个 buffer）拼凑起来。而 `start` 和 `finish` 就是在这个不连续的内存上，像两个“导航仪”一样，时刻界定着数据的真实边界，让上层用户感觉它是一个连续的整体。

```C++
template <class T, class Alloc=alloc,
          size_t BufSiz=0>
class deque {
    // 所谓 buffer size 是指每个 buffer 容纳的元素个数
public:
    typedef T value_type;
    typedef __deque_iterator<T,T,T*,BufSiz> iterator;
protected:
//定义中控数组指针类型
    typedef pointer* map_pointer; // T**
protected:
//声明 deque 的核心成员
    iterator start; 
    iterator finish;
    map_pointer map;                   *// 指向指针数组，元素类型是 T**
    size_type map_size;                *// map 这个指针数组的槽位数/容量*
public:
//提供基本接口
    iterator begin() { return start; }
    iterator end() { return finish; }
    size_type size() const { return finish - start; } 
    ...
};
```

###### deque如何模拟连续空间

对外提供的基本访问接口

为了让 `deque` 看起来像一个连续的数组，背后的迭代器默默扛下了所有跨 buffer 的指针跳跃、越界判断和中控数组寻址的复杂逻辑。

```C++
reference operator[](size_type n)//随机访问
{
    return start[difference_type(n)];
}

reference front()//获取首元素
    { return *start; }

reference back()//获取尾元素
{
    iterator tmp = finish;
    --tmp;
    return *tmp;
}

size_type size() const//计算元素总数
    { return finish - start; }

bool empty() const
    { return finish == start; }
```

在 C++ 中对于自定义类型的迭代器，如果没有特殊要求，尽量使用前加加 `++it`。从“最终状态”来看，效果是完全一致的。 但是，从表达式产生的值和性能开销来看，它们有着本质的区别。这也是为什么在 C++ 中，我们要特意重载两个不同版本的原因。

- 前加加（`++it`）：直接修改自己并返回自己的引用，没有临时对象的创建和销毁，效率高。

- 后加加（`it++`）：内部必须要创建一个临时对象 `tmp` 拷贝整个状态（对于复杂的迭代器，拷贝成本不低），再调用前++,然后再返回。效率相对较低。

##### **容器 rb_tree**

[一文带你彻底读懂红黑树（附详细图解）](https://zhuanlan.zhihu.com/p/91960960)

Red-Black tree（红黑树）是**平衡二元搜寻树**（balanced binary search tree）中常被使用的一种。平衡二元搜寻树的特征：排列规则有利 search 和 insert，并保持适度平衡，无任何节点过深。

rb_tree 提供“遍历”操作及 iterators。

按正常规则（++ite）遍历，便能获得排序状态（sorted）。

我们不应使用 rb_tree 的 iterators 改变元素值（因为元素有其严谨排列规则）。编程层面（programming level）并未阻绝此事。如此设计是正确的，因为 rb_tree 即将为 set 和 map 服务（作为其底部支持），而 map 允许元素的 data 被改变，只有元素的 key 才是不可被改变的。

rb_tree 提供两种 insertion 操作：insert_unique() 和 insert_equal()。

前者表示节点的 key 一定在整个 tree 中独一无二，否则安插失败；

后者表示节点的 key 可重复。

红黑树在 STL 内部是如何定义自己的:

```C++
template <class Key,
          class Value,
          class KeyOfValue,//为了代码复用，兼顾 set 和 map
          class Compare,
          class Alloc = alloc>//5 个模板参数
class rb_tree {
protected:
    typedef __rb_tree_node<Value> rb_tree_node;
    ...
public:
    typedef rb_tree_node* link_type;
    ...
protected:
    // RB-tree 只以三笔资料表现它自己
    size_type node_count;  // rb_tree的大小 (节点数量)
    link_type header;
    Compare key_compare;   // key的大小比较准则；应会是个 function object
    ...
};
```

**有序关联**（主流实现为红黑树）：

set/multiset 以 rb_tree 为底层结构，因此有「元素自动排序」特性。排序的依据是 key，而 set/multiset 元素的 value 和 key 合一：value 就是 key。

set/multiset 提供“遍历”操作及 iterators。按正常规则（++ite）遍历，便能获得排序状态（sorted）。

我们**无法**使用 set/multiset 的 iterators 改变元素值（因为 key 有其严谨排列规则）。set/multiset 的 iterator 是其底部的 RB tree 的 const-iterator，就是为了**禁止** user 对元素赋值。

**set 元素的 key 必须独一无二**，因此其 insert() 用的是 rb_tree 的 insert_**unique**()。

**multiset 元素的 key 可以重复**，因此其 insert() 用的是 rb_tree 的 insert_**equal**()。

|find()|按值查找，返回目标迭代器/尾迭代器|O(logn)|
|lower_bound()|大于等于目标的第一个元素的迭代器|O(logn)|
|upper_bound()|大于目标的第一个元素的迭代器|O(logn)|
|begin()|首迭代器|O(1)|
|end()|尾迭代器|O(1)|

###### 注意

1. **set 不要使用泛型的 lower_bound 和 upper_bound**，时间复杂度有问题

2. set 的移动迭代器 ++ 和 -- 操作的时间复杂度为 O(logn)

3. 不要边插边删

> **补充 · 为什么泛型版本会慢**：std::lower_bound 是「二分」，它靠 it + n 跳位置——但 set 的迭代器只能 ++/--，泛型算法只能退化成**线性前移**，O(n) 而不是 O(logn)。成员版 s.lower_bound(x) 直接在红黑树上二分，才是真 O(logn)。**凡是有同名成员版的算法，优先用成员版**（set::find、map::find、list::sort、list::remove…）。
> 
> 红黑树是「近似平衡」的二叉搜索树，最坏树高仍是 O(logn)，所以增删查都稳定在 O(logn)。代价是每个节点额外存颜色和三个指针，内存开销明显大于 vector。
>

###### map独特的operator[]

- `lower_bound` 是二分搜寻 (binary search) 的一种版本，试图在 sorted `[first,last)` 中寻找元素 value。若 `[first,last)` 拥有与 value 相等的元素(s)，便返回一个 iterator 指向其中第一个元素。如果没有这样的元素存在，便返回「假设该元素存在时应该出现的位置」。也就是说它会返回 iterator 指向第一个「不小于 value」的元素。如果 value 大于 `[first,last)` 内的任何一个元素，将返回 last。换句话说，`lower_bound` 返回的是「不破坏排序得以安插 value 的第一个适当位置」。

##### Hashtable

哈希表的核心是一个桶数组（Buckets Vector）。元素通过哈希函数算出一个值，决定放进哪个桶里。

#### 容器适配器

|适配器|语义|默认底层容器|说明|
|---|---|---|---|
|stack|后进先出 LIFO|deque|只暴露 push/pop/top/empty/size|
|queue|先进先出 FIFO|deque|只暴露 push/pop/front/back/empty/size|
|priority_queue|每次取最值（堆）|vector|只暴露 push/pop/top/empty/size|

为什么全部选择deque?（其实list也可以，但是内存碎片与缓存不友好）

stack和queue都不允许遍历，也不提供ite。默认选择deque是因为快。

stack可以选择vector，但是queue不行

- 对于 `stack`（先进后出）：
`vector` 其实是一个不错的选择。因为 `stack` 只需要在尾部 `push_back` 和 `pop_back`，`vector` 在这两端操作效率极高。
*但为什么没被选为默认？* 因为 `vector` 在扩容时，必须找一块更大的连续内存，并把老数据全部拷贝过去。如果数据量极大，这个瞬间的内存峰值和拷贝开销是不可忽视的。

- 对于 `queue`（先进先出）：
`vector` 是绝对不能用的。因为 `queue` 需要在头部 `pop_front()`。`vector` 如果要删除头部的元素，必须把后面所有的元素整体往前挪动一格，时间复杂度是 O(N)，效率极差。

map和set：无论是数据结构的功能、性能，还是内存开销，`map` 和 `set` 都完美避开了 `stack` 和 `queue` 的需求,没有高效的两端操作,功能完全冲突,内存开销巨大。

注意：

- **适配器不提供迭代器**，只暴露有限接口——所以不能对 stack 做 for 遍历，也不能传给 sort。

- 适配器可以换底层：stack\<int, vector\<int\>\>、queue\<int, list\<int\>\> 都合法（换的容器得支持所需操作）。

> **补充 · 三者的底层**：stack/queue 只是把底层容器的接口“掐头去尾”露出来；priority_queue 靠 make_heap / push_heap / pop_heap 这组堆算法维护 vector 里的完全二叉树结构，所以 top() 是 O(1)、push/pop 是 O(logn)，而它的迭代器？没有——堆的内部数组顺序不是有序的，暴露迭代器会误导人。

## 迭代器

### 迭代器标签（Iterator Tags）

```Thrift
// 五种 iterator category
struct input_iterator_tag {};
struct output_iterator_tag {};
struct forward_iterator_tag : public input_iterator_tag {};
struct bidirectional_iterator_tag : public forward_iterator_tag {};
struct random_access_iterator_tag : public bidirectional_iterator_tag {};
```

- `input_iterator_tag` 与 `output_iterator_tag` 并列。

- `forward_iterator_tag` 继承自 `input_iterator_tag`。

- `bidirectional_iterator_tag` 继承自 `forward_iterator_tag`。

- `random_access_iterator_tag` 继承自 `bidirectional_iterator_tag`。

#### 各大容器对号入座:

- 连续空间（Array, Vector, Deque）：支持直接跳到第 n 个元素，属于最强大的 `random_access_iterator_tag`。

- 双向链表（List） 和 红黑树（Set/Map）：能往前往后走，但不能瞬间跳跃。红黑树的 `++` 实际上是找中序遍历的下一个节点，属于 `bidirectional_iterator_tag`。

- 单向链表（Forward-List） 和 哈希表（Unordered_XXX）：为什么哈希表是单向的？回忆上一节讲哈希表底层链表，它只有一个 `next` 指针，没有 `prev`，只能往前找，属于 `forward_iterator_tag`。

#### istream_iterator 的 iterator_category

迭代器基类：告诉 STL 的算法新迭代器属于哪个 Category：

```C++

         typename _Pointer = _Tp*,
         typename _Reference = _Tp&>
struct iterator
{
    typedef _Category  iterator_category;
    typedef _Tp        value_type;
    typedef _Distance  difference_type;
    typedef _Pointer   pointer;
```

因为 STL 的迭代器不仅仅需要 iterator_category 这一个标签。它还需要另外 4 个属性（被称为迭代器的 5 个 Associated Types 关联类型）：

5. reference（元素引用类型）

如果你每次写一个新迭代器（比如 istream_iterator, list_iterator），都要手写这 5 个 typedef，极其繁琐且容易漏。

#### iterator_category对算法的影响

`std::advance(it, n)` 的作用是让迭代器 `it` 向前（或向后）移动 `n` 步。但是：

- 如果是 `vector`，有随机访问能力，直接 `it += n` 就能瞬间完成，时间复杂度 O(1)。

- 如果是 `list`，只能一步步挪，必须用 `while(n--) ++it;` 循环，时间复杂度 O(N)。

- 如果是 `forward_list`（单向），只能向前，如果 `n` 是负数，直接报错。

如果用 `if-else` 在运行时判断，每次调用都要付出判断代价。C++ 的做法是把它交给编译器，在编译期就决定调用哪段代码

**三个 ****`__advance`**** 重载版本**

```C++
//最弱的能力。不管三七二十一，硬循环 while(n--) ++i;。只支持向前。
template <class InputIterator, class Distance>
inline void __advance(InputIterator& i, Distance n, 
                      input_iterator_tag) { // 标注 ①
    while (n--) ++i;
}

//双向能力。判断 n 的正负，负数就往前走，正数就往后走。
template <class BidirectionalIterator, class Distance>
inline void __advance(BidirectionalIterator& i, Distance n, 
                      bidirectional_iterator_tag) { // 标注 ②
    if (n >= 0)
        while (n--) ++i;
    else
        while (n++) --i;
}

//最强能力。直接 i += n;。这是极致优化的体现，没有任何循环。
template <class RandomAccessIterator, class Distance>
inline void __advance(RandomAccessIterator& i, Distance n, 
                      random_access_iterator_tag) { // 标注 ③
    i += n;
}
```

**提取标签的辅助函数**

```C++
template <class Iterator>
inline typename iterator_traits<Iterator>::iterator_category
iterator_category(const Iterator&) {
    typedef typename iterator_traits<Iterator>::iterator_category category;
    return category();
}
```

**对外暴露的通用接口**

剥离出当前迭代器内部的 `iterator_category` 类型（即 `input` / `bidirectional` / `random_access`），并实例化一个该类型的空对象（标签）作为第三个参数传进去

```C++
template <class InputIterator, class Distance>
inline void advance(InputIterator& i, Distance n) {
    __advance(i, n, iterator_category(i));
}
```

#### iterator_category和type traits对算法的影响

**`std::copy()`**

![image.png](/images/uploads/stl-notes/stl-04.webp)

##### 第一层：最慢的“泛化”版本（左图黑框）

`while` 循环，一个一个地 `*result = *first`。

- 这个版本万能，什么 `list`、`set`、`deque` 都能用。

- 但它最慢，因为它每次都要判断 `first != last`，而且每次只能拷贝一个元素。

##### 第二层：进入“重载分发” (Tag Dispatching)

当你调用 `copy(...)` 时，它会进入 `__copy_dispatch`（注意左边提示框：函数模板不能偏特化，所以这里用的是函数重载）。
在这个阶段，STL 拿出了 `iterator_traits` 工具，看看你传进来的迭代器是不是“指针”。

- 如果是普通指针 `<T*, T*>`，进入 `__copy_t`。

- 如果是只读指针 `<const T*, T*>`，进入另一个 `__copy_t`。

##### 第三层：开启“暴力块拷贝” (特化)

如果发现你拷贝的是 `char*` 或 `wchar_t*`（图中的绿色粗箭头），那 STL 会直接掀桌子，底层调用 C 语言级别的 `memmove`。

- 】因为 `memmove` 是整块内存的直接拷贝，速度极快。对于 char 类型的数组，直接复制内存块比一个字符一个字符赋值快无数倍。

##### 第四层：类型的终极审判 (Type Traits)

如果你的指针不是 `char*` 而是普通的 `<T*, T*>`（比如 `int*` 或者自定义类的指针），怎么办？
这时候代码走到右侧下方的分支，祭出了另一大神器：`__type_traits`。

- STL 会判断这个类型 `T` 的赋值操作符（`operator=`）是不是 `trivial`（平凡的/无关痛痒的）。

    - 如果是 `int`、`float` 这种基本类型，它们的 `=` 就是内存直接覆盖，属于 `trivial op=`。STL 就会调用 `memmove`，极速拷贝。

    - 如果是带有复杂指针的类型（比如 `std::string`），它的 `=` 属于 `non-trivial`（非平凡，需要重新分配内存等）。这种绝对不能用 `memmove`（会导致浅拷贝内存泄漏），必须退回 `for` 循环，调用重载的 `=`。

##### 第五层：随机访问的专属优化 (强化)

看右侧标注的 `强化 -> __copy`。
如果传进来的是 `vector` 或 `deque` 的迭代器（RandomAccessIterator），STL 会走另外一条分支：`__copy_d()`。

- 普通版本是 `for(; first != last; ++first)`。每次循环都要判断一次 `!=`。

- 优化版本是：先算出总距离 `n = last - first`，然后执行 `for(; n > 0; --n)`。这样就省去了每次循环判断终点的开销。

**`std::destroy()`**** **

作用是销毁容器中的对象（调用它们的析构函数）。
如果有 1 万个 `int`，它们根本没有析构函数；如果有 1 万个带虚函数的对象，每个都需要调用析构函数。STL 怎么区分并优化？

STL 通过 Type Traits 在编译期“识别”类型特征，如果是 `trivial dtor` 或原生指针，直接变成 `no-op`（空操作）。

- trivial dtor (平凡析构)：编译器自动生成的、没有实际代码要执行的析构函数。

- non-trivial dtor (非平凡析构)：用户自定义的，或者内部包含需要释放内存等操作的析构函数。

- no-op (No Operation)：空操作，直接什么都不做，直接返回。

#### 算法源码中对 iterator_category 的“暗示”

##### 暗示 1：看模板参数名（最直接）

- 写着 `InputIterator` 的：要求最低，能 `++` 且能读 `*` 即可（如：`find`、`for_each`）。

- 写着 `BidirectionalIterator` 的：必须能后退 `--`（如：`reverse`、`copy_backward`）。

- 写着 `RandomAccessIterator` 的：必须能跳跃和相减 `it + n`、`last - first`（如：`sort`、`random_shuffle`）。

##### 暗示 2：看内部操作符

- 如果有 `--it`，必定是双向或随机。

- 如果有 `it + n` 或者 `last - first`，必定是随机访问。

- 如果全是 `++it`，那就是单向或以上。

##### 暗示 3：看是否调用 `iterator_traits`

- 如果直接写死类型名，说明算法有硬性要求（如 `sort` 绝不能接 `list`）。

- 如果内部用了 `iterator_traits` 并发生分发，说明算法是自适应的（如 `distance` 既支持 `list` 也支持 `vector`，性能表现不同）。
